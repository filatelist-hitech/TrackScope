Создать execution-план для: **$ARGUMENTS**

1. Прочитать @.codex/plans/PLANS.md и следовать его 10-секционному шаблону дословно.
2. Прочитать @CLAUDE.md и @AGENTS.md, чтобы заземлить план в контрактах проекта и anti-fake-правилах.
3. Классифицировать задачу: сложность (low / medium / high) и затронутые домены (dsp / mobile / ui / qa / docs / performance / security).
4. Перечислить субагентов, которым делегируется (например, `@dspman`, `@qaman`, `@archman`, `@reviewman`), и почему каждый нужен.
5. Перечислить точные файлы и папки для инспекции.
6. Описать текущее vs целевое поведение с конкретным evidence (пути файлов, имена функций, имена фикстур).
7. Указать тронутые контракты данных (поля DspResult, сигнатуры FFI, публичные API).
8. Разбить имплементацию на маленькие упорядоченные шаги. Тесты идут ВМЕСТЕ с каждым шагом, а не в конце.
9. Перечислить требуемые тесты и точные команды для запуска (cargo test, python3 -m unittest discover core/tests, отчёт offline-lab, flutter test для мобильного).
10. Перечислить риски и фолбэк для каждого.
11. Определить конкретные критерии приёмки.

Сохранить итоговый план в `docs/plans/<kebab-task-title>.md` (создать `docs/plans/`, если её нет). Если задача low-сложности — сказать это явно и пропустить полный шаблон, написать 5-строчное резюме вместо него.

Жёсткое правило: план никогда не должен предлагать фейковый/демо BPM, скрытые half/double-кандидаты или `STABLE` без evidence.
